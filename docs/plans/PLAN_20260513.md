# PLAN_20260513

## 주제

Cowork26 초기 방향: 브라우저 기반 협업 스프레드시트 PoC.

## 목표

소규모 팀이 웹 브라우저에서 Google Sheets처럼 시트를 만들고, 셀을 편집하고, 공동 작업자를 초대할 수 있는 협업 스프레드시트 서비스를 검토했다.

## 초기 확정 스택

| 영역 | 계획 |
|------|------|
| Frontend | React 19, Vite, TypeScript |
| Sheet UI | FortuneSheet |
| API | Vercel Functions |
| DB/Auth/Realtime | Supabase PostgreSQL, Auth, Realtime broadcast |
| Style | Tailwind CSS |
| Deploy | Vercel |

## 설계 요약

```txt
Browser
  - FortuneSheet UI
  - Supabase Realtime broadcast 구독

Vercel Functions
  - /api/sheets
  - /api/sheets/:id/cells
  - /api/sheets/:id/members

Supabase
  - profiles
  - sheets
  - sheet_members
  - cells
```

## DB 초안

초기 스프레드시트 PoC는 아래 테이블을 기준으로 설계했다.

```txt
profiles
- id
- display_name
- avatar_url
- created_at

sheets
- id
- title
- owner_id
- created_at
- updated_at

sheet_members
- sheet_id
- user_id
- role: editor | viewer
- joined_at

cells
- id
- sheet_id
- row
- col
- value
- formula
- updated_by
- updated_at
```

## MVP 범위

- 이메일 로그인
- 시트 생성 / 목록 / 삭제
- FortuneSheet 기반 셀 편집
- 셀 데이터 Supabase 저장 / 불러오기
- Supabase Realtime broadcast 기반 동기화
- 공동 작업자 초대

## 리스크

- 셀 편집 이벤트와 DB 저장, Realtime broadcast를 직접 맞춰야 한다.
- 권한 모델, viewer 편집 차단, 셀 삭제, 충돌 처리, presence/cursor를 별도로 구현해야 한다.
- 수식과 셀 상태 관리가 제품 복잡도를 빠르게 키운다.

## 결론

스프레드시트 PoC 설계는 보존하되, 이후 제품 방향은 Notion-lite 협업 문서 도구로 피벗했다. 현재 Next.js 앱에서는 `sheets`, `sheet_members`, `cells` 기반 기능은 사용하지 않는다.
