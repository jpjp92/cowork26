# PLAN_20260528

## 주제

Cowork26 DB/API 저장 및 불러오기 성능 최적화.

## 배경

페이지 전환 렌더링 쪽 1차 개선 이후, 로컬 dev 로그 기준 남은 병목은 API application-code 시간에 집중되어 있다.

관찰된 대표 로그:

```txt
GET /api/workspaces                         319ms ~ 2.2s
GET /api/pages?workspaceId=...              315ms ~ 603ms
GET /api/pages?id=...                       314ms ~ 498ms
PATCH /api/pages                            472ms ~ 1.318s
GET /api/workspaces/:id/members             3.6s
```

대부분 `next.js` 시간보다 `application-code` 시간이 크다. 즉 프론트 렌더링보다 Supabase auth/DB 왕복, 순차 쿼리, payload 크기, 자동저장 빈도 최적화가 다음 핵심이다.

## 목표

- 초기 진입과 워크스페이스 전환 시 API 응답 시간을 줄인다.
- 자동저장 `PATCH /api/pages` 요청 빈도와 1회 저장 비용을 줄인다.
- 불필요한 단일 페이지 fresh fetch를 줄이되, 다른 사용자 수정 반영 가능성은 유지한다.
- 성능 개선 중 권한 모델과 미저장 로컬 편집 보호 로직을 깨지 않는다.

## 현재 병목 가설

### 1. PATCH /api/pages 쿼리 왕복 과다

현재 저장 흐름은 대략 아래 순서다.

```txt
getUserFromRequest()
  -> supabaseAdmin.auth.getUser(token)

pages select workspace_id
  -> 저장 대상 page의 workspace 확인

requireWorkspaceRole()
  -> workspace_members select role

pages update
  -> update 후 전체 page row select
```

저장 1회에 Supabase 왕복이 여러 번 발생한다. 자동저장 특성상 이 비용이 반복된다.

### 2. 저장 payload가 클 수 있음

본문 저장은 `content` JSONB 전체를 보낸다. 문서가 커질수록 request body, DB update, response body 비용이 증가한다.

현재 update 후 응답도 `content`를 포함한 page 전체 row를 반환한다.

### 3. pages 목록 API가 content까지 포함

`GET /api/pages?workspaceId=...`가 페이지 트리용 metadata뿐 아니라 `content`까지 내려준다.

장점:
- 워크스페이스 진입 직후 페이지 클릭 시 로컬 content 즉시 표시 가능

단점:
- 페이지가 많거나 문서가 커질수록 워크스페이스 전환 비용 증가
- 초기 load가 무거워짐

### 4. workspaces/members API도 순차 조회 구조

`GET /api/workspaces`는 membership 조회 후 workspace 조회를 수행한다. 첫 요청에서 2초 이상이 나왔다.

`GET /api/workspaces/:id/members`는 한 번 3.6초가 나왔고, next.js 시간이 2.9초로 커서 dev 서버 컴파일 또는 route cold start 영향도 섞여 있다.

## 단계별 계획

## Phase 1 — 계측 추가

구현 전에 API 내부 구간별 시간을 로그로 나눈다.

대상:
- `GET /api/workspaces`
- `GET /api/pages?workspaceId=...`
- `GET /api/pages?id=...`
- `PATCH /api/pages`
- `GET /api/workspaces/:id/members`

측정 구간 예시:

```txt
auth.getUser
role check
page select
page update
workspace select
members select
response json
```

목표:
- 느린 구간이 auth인지, DB select/update인지, payload인지 분리
- dev 서버 컴파일/cold start와 실제 application-code 병목 분리

적용 방식:
- development에서만 `console.time` 또는 `performance.now()` 기반 로그 출력
- production 로그 오염 방지

## Phase 2 — PATCH /api/pages 저장 최적화

가장 우선 적용할 영역이다. autosave가 반복되므로 체감 영향이 크다.

### 2-1. title 저장과 content 저장 경로 분리 검토

title 변경은 content를 다룰 필요가 없다.

가능한 응답:

```txt
title 저장 -> id, title, updated_at 중심 반환
content 저장 -> id, content, updated_at 반환 또는 id, updated_at만 반환
```

단, 클라이언트가 저장 후 `pages` state를 갱신하는 방식과 충돌하지 않아야 한다.

### 2-2. update response payload 축소

현재는 update 후 page 전체 row를 반환한다.

검토안:
- content 저장 성공 시 `id, updated_at, updated_by`만 반환
- 클라이언트는 이미 `pendingContent`를 알고 있으므로 server content echo를 꼭 받을 필요가 없음
- title 저장은 `id, title, updated_at` 반환

주의:
- DB trigger가 수정한 `updated_at`은 받아야 함
- 서버 normalize가 필요한 필드(title trim 등)는 반환 필요

### 2-3. 권한 확인 쿼리 수 축소

현재는 page 조회 후 role 확인을 따로 한다.

검토안:
- DB 함수/RPC로 `page update + role check`를 한 번에 수행
- 또는 Supabase query를 join/exists 형태로 줄일 수 있는지 확인

단기적으로는 코드 변경 범위가 큰 RPC보다 payload 축소와 autosave 빈도 조정부터 적용한다.

### 2-4. autosave 빈도 조정

현재 본문 저장 debounce는 1.5초다.

검토안:
- 1.5초 -> 2.5초
- 같은 content JSON이면 저장 생략
- content save in-flight 중 새 변경이 생기면 완료 후 최신본만 한 번 더 저장

목표:
- 타이핑 중 PATCH 연속 발생 감소
- 저장 안정성 유지

## Phase 3 — pages 불러오기 전략 정리

현재 목록 API가 content까지 포함한다. 단기와 장기를 나눠 접근한다.

### 3-1. 단기: 현재 구조 유지 + TTL 활용

이미 적용한 30초 TTL로 `GET /api/pages?id=...` 반복 호출을 줄인다.

유지 이유:
- 페이지 클릭 즉시 content 표시 가능
- 변경 범위 작음

추가 검토:
- manual refresh 시 TTL 무시하고 강제 revalidate
- 저장 성공 시 해당 page timestamp 갱신

### 3-2. 중기: metadata 목록 API와 content API 분리

페이지 수와 문서 크기가 커지면 아래 구조가 더 안정적이다.

```txt
GET /api/pages?workspaceId=...&mode=tree
  -> id, workspace_id, parent_id, title, order_index, updated_at

GET /api/pages?id=...
  -> 단일 page content
```

클라이언트는 page content cache를 둔다.

주의:
- 첫 페이지 표시가 단일 page fetch에 의존하게 되므로 skeleton/optimistic display 설계 필요
- 다중 사용자 최신본 반영 정책 필요

## Phase 4 — workspaces/members 조회 최적화

### 4-1. GET /api/workspaces

현재 흐름:

```txt
workspace_members by user
workspaces in workspaceIds
server-side merge/sort
```

검토안:
- Supabase join으로 한 번에 가져올 수 있는지 확인
- `workspace_members(user_id, order_index)` composite index 추가 검토
- `workspaces(id)`는 PK라 문제 가능성 낮음

### 4-2. GET /api/workspaces/:id/members

3.6초 로그는 dev route compile/cold start 영향이 섞여 있을 수 있다.

우선:
- 같은 endpoint를 두 번째 호출했을 때 시간 재확인
- 내부 계측 후 auth, role check, members query 중 어디가 느린지 판단

## Phase 5 — DB 인덱스 점검

현재 주요 인덱스:

```sql
workspace_members_user_id_idx ON workspace_members(user_id)
pages_workspace_id_idx ON pages(workspace_id)
pages_parent_id_idx ON pages(parent_id)
```

추가 검토 후보:

```sql
-- workspace list 정렬
CREATE INDEX IF NOT EXISTS workspace_members_user_order_idx
ON workspace_members(user_id, order_index, created_at);

-- page tree 정렬
CREATE INDEX IF NOT EXISTS pages_workspace_order_idx
ON pages(workspace_id, parent_id, order_index, created_at);
```

적용 전 확인:
- Supabase query plan 또는 실제 로그로 병목 확인
- 작은 데이터셋에서는 인덱스 효과보다 네트워크 왕복이 더 클 수 있음

## 우선순위

1. API 내부 계측 추가
2. `PATCH /api/pages` 응답 payload 축소
3. autosave debounce 및 중복 저장 방지 강화
4. `GET /api/workspaces` join/index 검토
5. pages metadata/content 분리 설계

## 성공 기준

로컬 dev warm 상태 기준 목표:

```txt
GET /api/workspaces                 300ms 이하 안정화
GET /api/pages?workspaceId=...      300ms 이하 안정화
PATCH /api/pages                    300ms ~ 500ms 범위로 안정화
GET /api/pages?id=...               호출 빈도 최소화
```

운영 환경에서는 dev compile/cold start 영향이 없으므로 별도 측정이 필요하다.

## 리스크

- payload 축소 시 클라이언트 `pages` state 갱신 로직이 깨질 수 있음
- autosave debounce 증가 시 저장 완료 체감이 늦어질 수 있음
- content API 분리 시 첫 페이지 표시 정책이 복잡해질 수 있음
- RPC 도입은 성능에는 유리할 수 있으나 Supabase SQL 관리 부담 증가

5. autosave 중복 저장 방지 적용
