# DEV_260528 — 페이지 전환 지연 검토

## 요약

웹에서 페이지를 전환할 때 발생하는 짧은 딜레이 원인을 코드 기준으로 검토했다. 현재 구조는 페이지 클릭 시 즉시 로컬 상태를 바꾸지만, 동시에 서버 최신본을 다시 요청하고 Tiptap 에디터를 페이지마다 재마운트한다. 네트워크 왕복, Supabase API 순차 호출, 무거운 에디터 초기화 비용이 합쳐져 체감 지연이 발생할 가능성이 높다.

## 확인한 주요 원인

### 1. 페이지 선택 시 단일 페이지를 매번 재조회

`selectActivePage()`가 `loadingPageId`를 설정하고 `activePageId`를 변경한다. 이후 `activePageId` 변경 effect에서 `/api/pages?id={activePageId}`를 호출해 서버 최신 content를 가져온다.

관련 위치:
- `components/notion-lite-app.tsx` — `selectActivePage`
- `components/notion-lite-app.tsx` — active page fresh fetch effect

의도는 다른 사용자의 수정본을 반영하는 것이지만, 이미 `loadPages()`로 content를 받아온 상태에서도 전환마다 네트워크 요청이 발생한다.

### 2. fetch 완료 전까지 에디터가 비활성화됨

`activePageLoading`이 true인 동안 title input과 `DocumentEditor`의 `editable`이 false가 된다. 실제 화면은 바뀌어도 입력이 잠깐 막히므로 사용자는 페이지 전환이 늦다고 느낄 수 있다.

관련 위치:
- `components/notion-lite-app.tsx` — `activePageLoading`
- `components/notion-lite-app.tsx` — title input `disabled`
- `components/notion-lite-app.tsx` — `DocumentEditor editable`

### 3. 페이지마다 DocumentEditor 재마운트

`DocumentEditor`에 `key={activePage.id}`가 걸려 있어 페이지를 바꿀 때마다 에디터 인스턴스가 완전히 새로 생성된다.

Tiptap 에디터는 확장 구성이 무겁다.
- StarterKit
- CodeBlockLowlight
- MermaidBlock
- Table / TableRow / TableCell / TableHeader
- Placeholder
- 커스텀 paste handler와 row resize handler

관련 위치:
- `components/notion-lite-app.tsx` — `DocumentEditor key={activePage.id}`
- `components/document-editor.tsx` — `useEditor`

### 4. Mermaid가 에디터 모듈 로딩 시 항상 포함됨

`document-editor.tsx`에서 `mermaid`를 top-level import하고 즉시 initialize한다. Mermaid 블록이 없는 페이지에서도 에디터 청크 로딩 및 초기화 비용에 포함된다.

관련 위치:
- `components/document-editor.tsx` — `import mermaid from 'mermaid'`
- `components/document-editor.tsx` — `mermaid.initialize(...)`

### 5. API 단일 페이지 조회가 Supabase 호출을 여러 번 수행

`GET /api/pages?id=...`는 요청마다 아래 순서로 동작한다.

1. `getUserFromRequest()`에서 `supabaseAdmin.auth.getUser(token)`
2. `pages` 테이블에서 page 조회
3. `requireWorkspaceRole()`에서 `workspace_members` 조회

관련 위치:
- `app/api/_utils/auth.ts`
- `app/api/pages/route.ts`

각 호출이 순차로 수행되므로 네트워크 상태와 Supabase 응답 시간에 따라 페이지 전환 딜레이가 커질 수 있다.

## 빌드 / 번들 관찰

production build는 통과했다.

```bash
npm run build
npm run typecheck
```

참고 측정값:
- `.next/static` JS 총량: 약 4.86MB uncompressed
- gzip 기준 JS 총량: 약 1.37MB
- 큰 JS 청크: 약 616KB, 572KB, 419KB 등
- `node_modules/mermaid`: 약 76MB
- `node_modules/@tiptap`: 약 8.8MB

개발 환경 산출물에서는 Mermaid 관련 청크가 1MB 이상 단위로 확인되어, 에디터 초기 로딩 및 전환 비용에 영향을 줄 가능성이 있다.

## 로컬 실행 로그 관찰

로컬 dev 서버에서 확인한 응답 시간 기준:

- `GET /api/workspaces`: 약 3.0s
  - Next.js: 약 1.075s
  - application-code: 약 1.920s
- `GET /api/pages?workspaceId=...`: 약 661ms ~ 1.404s
- `GET /api/pages?id=...`: 대체로 약 322ms ~ 517ms, 한 번은 약 952ms

해석:
- 페이지 전환 단일 조회는 Next.js 처리보다 `application-code` 시간이 대부분을 차지한다.
- `/api/pages?id=...`는 auth 확인, page 조회, role 확인을 순차로 수행하므로 Supabase 왕복 시간이 그대로 전환 로그에 누적된다.
- 초기 `loadPages()`가 이미 content를 포함해 내려주는데도, 페이지를 클릭할 때마다 단일 page fresh fetch가 반복되어 빠른 페이지 탐색 시 API 요청이 과하게 발생한다.

## 개선 방향

### 1. 전환 즉시 로컬 content 표시 + background revalidate

현재 `pages` 상태에 이미 content가 있으므로 클릭 직후에는 로컬 content를 즉시 보여주고, 서버 최신본 조회는 background로 처리한다. fetch 완료 전에도 에디터를 막지 않는 방향을 우선 검토한다.

주의점:
- 미저장 local content가 있는 페이지는 서버 응답으로 덮어쓰면 안 됨
- 현재 `pendingContent`, `saveTimers`, `contentSaveInFlight` 보호 로직은 유지 필요

### 2. `DocumentEditor key={activePage.id}` 제거 검토

에디터 인스턴스를 매번 버리지 않고 `content` prop 변경 시 `setContent`로 교체하는 구조를 검토한다. 이미 `document-editor.tsx`에는 prop content 변경 시 `editor.commands.setContent(...)`를 호출하는 effect가 있으므로, key 제거 가능성이 있다.

검증 필요:
- 페이지 전환 시 이전 페이지 내용이 잠깐 남지 않는지
- autosave가 잘못 호출되지 않는지
- selection/focus 상태가 이상하게 유지되지 않는지

### 3. Mermaid lazy import

Mermaid는 실제 mermaid block 렌더링 시점에만 import하도록 변경한다.

예상 효과:
- 기본 에디터 로딩 청크 축소
- Mermaid를 쓰지 않는 일반 문서 전환 비용 감소

### 4. pages 목록 API payload 분리

장기적으로는 `GET /api/pages?workspaceId=...`가 전체 content까지 내려주는 구조를 재검토한다.

가능한 방향:
- 목록 API: id, title, parent_id, order_index, updated_at 중심
- 단일 페이지 API: 선택 시 content 조회
- 클라이언트 cache: 한 번 연 page content 보관

현재는 이미 목록 fetch가 content를 포함하므로, 단기 개선은 background revalidate 쪽이 더 영향이 작다.

### 5. 실제 지연 구간 계측

체감 추정보다 정확한 판단을 위해 아래 구간에 `performance.mark`를 넣어 측정한다.

- page row click
- `activePageId` state 반영
- `/api/pages?id=...` 응답 수신
- `DocumentEditor` content apply 완료

## 적용한 수정

### 1. 페이지 fresh fetch 중 에디터 비활성화 제거

`loadingPageId` state를 제거했다. 서버 최신본 조회는 background로 수행하지만, 그동안 title input과 `DocumentEditor`를 비활성화하지 않도록 변경했다.

효과:
- 페이지 클릭 직후 로컬 content를 기준으로 계속 편집 가능
- fresh fetch 응답 대기 시간이 입력 지연으로 느껴지는 문제 완화

관련 파일:
- `components/notion-lite-app.tsx`

### 2. background fetch 중 autosave 차단 제거

`loadingPageIdRef`가 남아 있으면 fetch 중 사용자가 입력한 내용의 autosave가 무시될 수 있어 ref 기반 차단도 제거했다. 서버 fresh 응답이 도착했을 때는 기존 `pendingContent`, `saveTimers`, `contentSaveInFlight` 체크로 미저장 로컬 편집을 덮어쓰지 않도록 유지했다.

관련 파일:
- `components/notion-lite-app.tsx`

### 3. page fresh fetch TTL 추가

`PAGE_REVALIDATE_INTERVAL_MS = 30_000`을 추가했다. `loadPages()`로 받은 페이지들은 즉시 fresh 상태로 기록하고, 30초 안에 같은 페이지를 선택하면 `/api/pages?id=...` 재조회는 생략한다.

효과:
- 워크스페이스 진입 직후 페이지를 빠르게 넘길 때 단일 page API 반복 호출 감소
- 로컬 content 즉시 표시 전략과 충돌하지 않음
- 생성/저장/fresh fetch 성공 시 timestamp 갱신
- 페이지 삭제 시 timestamp 정리

관련 파일:
- `components/notion-lite-app.tsx`

### 4. DocumentEditor 재마운트 제거

`DocumentEditor`에 걸려 있던 `key={activePage.id}`를 제거했다. 페이지 전환 시 에디터 인스턴스를 매번 새로 만들지 않고, 기존 `content` prop 변경 effect가 `editor.commands.setContent(..., { emitUpdate: false })`로 내용을 교체하도록 했다.

효과:
- Tiptap 에디터 초기화 반복 감소
- 페이지 전환 시 확장 구성 재생성 비용 감소

관련 파일:
- `components/notion-lite-app.tsx`
- `components/document-editor.tsx`

### 5. Mermaid lazy import

`mermaid` top-level import와 즉시 initialize를 제거했다. Mermaid block을 실제로 렌더링할 때만 `import('mermaid')`를 수행하고, 최초 1회 initialize한 인스턴스를 재사용하도록 변경했다.

효과:
- Mermaid를 쓰지 않는 일반 문서에서 에디터 기본 로딩 비용 감소
- 에디터 모듈 초기 평가 시 Mermaid 초기화 제거

관련 파일:
- `components/document-editor.tsx`

### 6. API 내부 timing 계측 추가

DB/API 병목 구간을 확인하기 위해 development 전용 timing helper를 추가했다. `NODE_ENV !== 'production'`에서만 `[api-timing]` 로그를 출력한다.

계측 대상:
- `auth.getUser`
- workspace role 조회
- page/workspace/membership select
- page insert/update/delete
- request body parse
- workspace merge/sort
- Supabase Auth Admin `listUsers`

예상 로그 형태:

```txt
[api-timing] PATCH /api/pages auth.getUser=120ms request.json=1ms page.lookup=90ms role.select=95ms page.update=350ms patchType=content total=656ms
```

초기 계측 결과:

```txt
GET /api/workspaces
auth.getUser=2753ms memberships.select=191ms workspaces.select=310ms merge.sort=8ms total=3292ms

GET /api/pages?workspaceId=...
auth.getUser=113ms role.select=130ms pages.select=250ms total=501ms

GET /api/pages?id=...
auth.getUser=1254ms page.select=517ms role.select=224ms total=2005ms
auth.getUser=347ms page.select=140ms role.select=128ms total=621ms
auth.getUser=140ms page.select=124ms role.select=147ms total=421ms
```

해석:
- 첫 번째 큰 병목은 `supabaseAdmin.auth.getUser(token)`이다.
- warm 상태에서도 `auth.getUser`가 140ms~350ms 정도를 차지하고, cold/느린 요청에서는 1.2s~2.7s까지 튄다.
- DB select 자체는 대체로 100ms~300ms 범위이며, 아주 느린 단일 page 조회에서는 `page.select=517ms`도 확인됐다.
- 다음 최적화는 DB 쿼리 자체보다 서버 요청마다 auth token을 검증하는 비용을 줄이는 방향을 먼저 검토해야 한다.

추가 계측:

```txt
GET /api/workspaces
auth.getUser=769ms memberships.select=138ms workspaces.select=112ms rss=711MB heap=83MB total=1022ms

GET /api/pages?workspaceId=...
auth.getUser=105ms role.select=121ms pages.select=181ms rss=715MB heap=91MB total=410ms

GET /api/workspaces/[id]/members
auth.getUser=171ms role.select=102ms members.select=147ms auth.admin.listUsers=245ms rss=696MB heap=103MB total=665ms
```

해석:
- API 요청 시점의 Node 메모리는 `rss=696~715MB`, `heap=83~103MB`로 안정적이다.
- `auth.getUser` 지연은 로컬 JS heap/GC 문제보다는 Supabase Auth 왕복 또는 첫 연결 초기화 비용일 가능성이 높다.
- members API는 `auth.admin.listUsers`도 245ms를 차지하므로 이후 별도 개선 후보.

### 7. auth.getUser 짧은 TTL cache 추가

같은 화면에서 연속 API 요청이 여러 개 발생하므로, token별 user 검증 결과를 10초만 메모리에 캐시하도록 변경했다.

설계:
- token 전체 문자열을 key로 사용
- 성공한 `auth.getUser` 결과만 캐시
- 실패한 토큰은 캐시하지 않음
- TTL: 10초
- 최대 cache size: 100
- 같은 token으로 동시 요청이 들어오면 in-flight promise를 공유
- timing 로그에 `auth.cacheHit` 또는 `auth.inflightHit` 표시

관련 파일:
- `app/api/_utils/auth.ts`

재측정 결과:

```txt
GET /api/workspaces
auth.getUser=812ms memberships.select=159ms workspaces.select=126ms total=1107ms

GET /api/pages?workspaceId=...
auth.cacheHit=0ms role.select=132ms pages.select=280ms total=415ms
```

결론:
- auth cache가 정상 동작한다.
- 연속 API 요청에서 `auth.getUser` 왕복이 제거됐다.
- 다음 개선 후보는 `role.select` TTL cache와 `pages.select` payload 계측이다.

관련 파일:
- `app/api/_utils/timing.ts`
- `app/api/_utils/auth.ts`
- `app/api/pages/route.ts`
- `app/api/workspaces/route.ts`
- `app/api/workspaces/[id]/members/route.ts`
