# DEV_260618 — 페이지·워크스페이스 이동 레이턴시 개선 (적용 + 측정 계획)

## 요약

페이지 이동·워크스페이스 전환 시의 체감 지연을 검토하고, 위험이 낮은 두 가지(클라이언트 SWR 캐시 + 서버 role 캐시)를 먼저 적용했다. dev 서버 로그로 측정한 결과 두 캐시는 의도대로 동작했으나, 실제 시간을 지배하는 병목은 `auth.getUser` 네트워크 왕복과 Supabase까지의 쿼리 RTT(리전 거리)로 드러났다. 이 둘은 보류했던 항목(JWT 로컬 검증, 리전 코로케이션)을 가리키며, dev 수치는 WSL2→클라우드라 과장되어 있어 **프로덕션 실측 후 재판단**하기로 했다.

설계 상세는 `docs/superpowers/specs/2026-06-18-navigation-latency-design.md` 참고.

## 진단 (현재 구조의 지연 원인)

- **클라이언트**: 단일 클라이언트 컴포넌트(`notion-lite-app.tsx`)가 모든 fetch를 직접 호출. 워크스페이스별 페이지 캐시가 없어 A→B→A 전환마다 스켈레톤 + 전체 재요청.
- **서버 왕복**: 모든 `/api/*` 요청이 `auth.getUser`(10초 캐시 있음) + `requireWorkspaceRole`(캐시 없음) + 실제 쿼리를 순차로 수행 → 요청당 Supabase 2~3회 왕복. supabase-js는 REST(HTTPS)라 커넥션 풀 문제가 아니라 **왕복 횟수·RTT**가 원인.

## 적용한 변경 (Tier 1·2)

### 1. 클라이언트 — 워크스페이스별 페이지 SWR 캐시 (`components/notion-lite-app.tsx`)

- `pagesCache = useRef(Map<workspaceId, PageRecord[]>)` 추가.
- **전환 effect**: 캐시 히트 시 스켈레톤 없이 즉시 표시 + 백그라운드 재검증, 미스 시 기존처럼 스켈레톤 + fetch.
- **캐시 동기화 effect**: `pages` 변경을 캐시에 자동 반영(`pages[0].workspace_id === activeWorkspaceId` 가드로 전환 레이스 차단, 빈 배열은 `loadPages`가 책임). 모든 mutation 호출부 무수정.
- **`loadPages(workspaceId, { background })`**: background면 `pagesLoading` 미설정. 응답 반영은 `workspaceId === activeWorkspaceIdRef.current`일 때만(늦게 온 응답 무시). 캐시는 항상 workspaceId 키로 갱신.
- **reconcile (저장 손실 방지)**: `setPages` 전에 `saveTimers`/`contentSaveInFlight`/`pendingContent` 중 하나라도 있는 페이지는 content를 로컬 우선으로 보존, 구조 변경(parent/order/title)만 서버 값 수용. 단건 재검증 effect와 동일 원칙.
- 로그아웃 시 `pagesCache.clear()` + `pagesRef = []`.
- 추가 ref: `activeWorkspaceIdRef`, `pagesRef`.

### 2. 서버 — `requireWorkspaceRole` role 캐시 (`app/api/_utils/auth.ts`)

- `roleCache = Map<\`${userId}:${workspaceId}\`, { role, expiresAt }>`, TTL 5초, max 200, prune 함수.
- 캐시 히트 시 저장된 **role 문자열**을 호출 인자 `roles` 배열과 대조(불리언 캐싱 금지 — 엔드포인트별 허용 role이 달라 섞임).
- 멤버일 때만 캐싱(비멤버 negative 제외). `timing.mark('role.cacheHit')` 추가.

## 보류 (Tier 3 — 향후 과제)

- **JWT 로컬 검증(jose)**: `auth.getUser` 네트워크 왕복 제거. env(JWT 시크릿/JWKS) 추가 필요로 이번 범위 제외.
- **사이드바 메타/본문 분리**: 페이지 수가 커지면 도입.
- **Vercel ↔ Supabase 리전 코로케이션 점검**.

## 검증 결과 (dev 서버, WSL2 → Supabase 클라우드)

### 정적 검증 (통과)
- `npm run typecheck` 통과, dev HMR 재컴파일·모듈 로드 에러 없음, API 정상 응답.

### 로그 측정 — 캐시는 동작, 그러나 병목은 다른 곳

- ✅ role 캐시 동작 확인: 같은 워크스페이스 연속 요청에서 `role.cacheHit=0ms`(특히 `mode=single` 페이지 fetch). 다른 워크스페이스로 전환 시 캐시 키가 달라 miss(정상).
- ⚠️ 실제 지배적 비용:
  - `auth.getUser` = 200~1200ms (가장 큼). 캐시 miss 시 1초씩.
  - 단순 인덱스 조회 1건이 100~500ms (`pages.select`, `memberships.select`) → Supabase RTT가 멀다는 신호(리전 의심).
  - 최악 사례: `GET /api/workspaces total=1808ms` = auth.getUser 1007ms + memberships 531ms + workspaces 268ms (순차).
- ⚠️ 주의: dev 수치는 WSL2→클라우드라 집/사무실 인터넷 RTT 포함 → 과장됨. 프로덕션(Vercel 함수 ↔ 같은 리전 Supabase)이면 훨씬 낮음.

### 수동 테스트 체크리스트 (브라우저, 미완)
1. 워크스페이스 전환: A→B→A 두 번째 A 진입에서 스켈레톤 미표시 + 백그라운드 `GET /api/pages?workspaceId=A` 1회.
2. **저장 손실 레이스(중요)**: A 편집(저장 디바운스 중) → 즉시 B→A 복귀 → 편집 유지, 저장 후 옛 내용으로 되돌아가지 않음.
3. role 캐시: 로그에서 `role.cacheHit=0ms` 확인.

   - **JWT 로컬 검증** 도입 (auth.getUser 왕복 제거).
3. 페이지 수 증가 시 사이드바 메타/본문 분리 검토.
