# DEV_260722 — 워크스페이스·페이지 URL 동기화 및 부드러운 화면 전환

## 요약

기존에는 워크스페이스와 페이지 선택 상태가 React 컴포넌트 내부에만 있어 주소가 항상 `/`로 유지됐다. 선택 상태를 URL에 반영해 특정 페이지의 직접 접속, 새로고침, 링크 공유, 브라우저 뒤로/앞으로 이동을 지원하도록 변경했다.

초기 구현에서는 Next.js `router.push()`와 `router.replace()`로 동적 라우트를 이동했으나, 페이지 전환마다 라우트가 다시 평가되면서 앱 화면 전체가 전환되는 느낌이 강했다. 편집기 앱에 적합하도록 React 화면 상태는 유지하고 브라우저 History API로 URL만 갱신하는 방식으로 최종 수정했다.

## URL 구조

추가한 경로:

```txt
/w/{workspaceId}
/p/{pageId}
/w/{workspaceId}/p/{pageId}  # 기존 링크 호환
```

- 워크스페이스 선택 시 워크스페이스 경로를 기록한다.
- 페이지 선택 시 전역 고유 page ID만 기록해 URL 길이를 줄인다.
- 짧은 페이지 URL로 직접 접속하면 단일 페이지 API 응답의 `workspace_id`로 소속 워크스페이스를 자동 선택한다.
- 기존 긴 페이지 URL은 계속 열 수 있으며 페이지 확인 후 짧은 URL로 정규화한다.
- 루트(`/`)로 로그인하면 접근 가능한 첫 워크스페이스와 첫 페이지를 선택하고 URL을 현재 선택에 맞게 교체한다.
- URL의 워크스페이스 또는 페이지에 접근할 수 없으면 접근 가능한 첫 항목으로 선택과 URL을 보정한다.
- 페이지 생성·삭제 및 실패 롤백 시에도 현재 선택과 URL을 일치시킨다.

## 직접 접속용 동적 라우트

Vercel 프로덕션과 로컬 개발 서버에서 깊은 경로로 직접 접속하거나 새로고침할 때 404가 발생하지 않도록 App Router 동적 라우트를 추가했다.

- `app/w/[workspaceId]/page.tsx`
- `app/p/[pageId]/page.tsx`
- `app/w/[workspaceId]/p/[pageId]/page.tsx`

각 라우트는 경로 파라미터를 `NotionLiteApp`의 초기 선택값으로 전달한다. 별도의 Vercel rewrite 설정은 필요하지 않다.

## 화면 전환 방식

### 초기 구현의 문제

Next.js 라우터로 페이지 경로를 이동하면 URL은 정상적으로 변경되지만 서버 라우트와 컴포넌트 트리가 다시 평가된다. 이 앱은 사이드바와 문서 편집기를 계속 유지하면서 선택한 문서 데이터만 바꾸는 구조이므로, 일반적인 페이지 라우팅은 전환 시 시각적 변화가 지나치게 컸다.

### 최종 구현

`components/notion-lite-app.tsx`에서 Next.js 라우터 호출을 제거하고 다음 방식으로 변경했다.

```ts
window.history.pushState(state, '', path)
window.history.replaceState(state, '', path)
```

- 사용자가 워크스페이스나 페이지를 선택하면 `pushState`로 방문 기록을 추가한다.
- 첫 항목 자동 선택, 접근 불가능한 ID 보정, 생성·삭제 롤백처럼 현재 기록을 교정하는 경우 `replaceState`를 사용한다.
- 동일한 경로면 History API를 다시 호출하지 않는다.
- 기존 `window.history.state`를 보존해 Next.js가 관리하는 브라우저 기록 상태를 덮어쓰지 않는다.
- URL 변경과 함께 기존 React 선택 상태를 즉시 갱신하므로 사이드바와 앱 셸은 유지되고 문서 내용만 교체된다.

## 뒤로/앞으로 가기

`popstate` 이벤트를 구독해 다음 경로 형식을 파싱한다.

```txt
/w/:workspaceId
/p/:pageId
/w/:workspaceId/p/:pageId
```

브라우저 기록을 이동하면 먼저 현재 페이지 목록과 워크스페이스별 캐시에서 page ID를 찾는다. 캐시에 없으면 권한 검사가 포함된 단일 페이지 API로 `workspace_id`를 해석한다. 빠르게 뒤로/앞으로 이동할 때는 요청 sequence와 현재 URL을 다시 확인해 늦은 응답이 최신 선택을 덮어쓰지 않게 했다.

로그인된 실제 브라우저에서는 다음 항목을 추가로 확인한다.

1. 워크스페이스와 페이지 전환 시 앱 전체가 새로고침되는 느낌 없이 내용만 교체되는지 확인한다.
2. 페이지 URL을 복사해 새 탭에서 열었을 때 같은 페이지가 선택되는지 확인한다.
3. 새로고침 후 선택 상태가 유지되는지 확인한다.
4. 브라우저 뒤로/앞으로 이동 시 선택 상태와 URL이 일치하는지 확인한다.

## URL 단축 구현

페이지 UUID는 `pages.id` 기본키로 전체 시스템에서 고유하다. 페이지 전용 주소에서 중복 정보인 workspace UUID를 제거해 다음처럼 단순화했다.

```txt
기존: /w/{workspace UUID}/p/{page UUID}
현재: /p/{page UUID}
```

직접 접속 시 워크스페이스 목록과 단일 페이지를 병렬 조회한다. 페이지 API가 기존 멤버십 권한을 확인한 후 반환한 `workspace_id`가 사용자의 워크스페이스 목록에도 존재할 때만 페이지를 화면에 반영한다. 이 해석이 끝나기 전에는 기본 워크스페이스 선택이 요청 page ID를 덮어쓰지 않도록 pending 흐름과 ref 순서를 유지한다.

UUID 자체도 더 줄여야 한다면 후속 단계에서 DB에 고유한 8~12자리 `short_id`를 추가해 `/p/{shortId}` 형태로 확장한다. 이 단계는 backfill, 충돌 정책, 기존 UUID 링크 호환이 필요하므로 별도 마이그레이션으로 진행한다.
