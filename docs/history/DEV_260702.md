# DEV_260702 — Excel 붙여넣기 이미지 삽입/페이지 저장 500 에러 수정 및 사이드바 depth 접힘 기능

## 요약 (1) Excel 붙여넣기 → 이미지 삽입 문제

Excel에서 셀 범위를 복사해 에디터에 붙여넣으면 표가 아니라 셀 영역을 렌더링한 이미지(PNG)로 삽입되는 문제를 조사하고 수정했다.

원인은 `handlePaste`가 클립보드의 `image/*` 항목을 가장 먼저 검사·처리하는 구조였는데, Excel은 셀 복사 시 `text/html`(`<table>`)·`text/plain`(TSV)과 함께 셀 영역을 렌더링한 `image/png`를 항상 클립보드에 동봉하기 때문에, 표 데이터에 도달하기 전에 이미지 분기가 먼저 매칭되어 종료된 데 있었다.

## 원인 분석

확인된 증상:

- 외부(Excel)에서 셀들을 복사해 페이지에 붙여넣으면 표가 아니라 이미지로 들어간다.

붙여넣기 경로: `components/document-editor.tsx`의 `handlePaste(view, event)`.

```ts
handlePaste(view, event) {
  const imageFile = Array
    .from(event.clipboardData?.items ?? [])
    .find(item => item.type.startsWith('image/'))
    ?.getAsFile()

  if (imageFile && onUploadImageRef.current) {
    event.preventDefault()
    // ... PNG를 Storage에 업로드하고 <img> 노드 삽입
    return true          // ← 여기서 종료, text/html의 <table>은 검사되지 않음
  }
  // ...
}
```

근본 원인:

- 데스크톱 Excel은 셀 범위를 복사하면 클립보드에 `text/html`(`<table>` 마크업), `text/plain`(탭 구분 텍스트), `image/png`(셀 영역 렌더링 비트맵)를 **동시에** 담는다. `image/png`는 "그림으로 붙여넣기"를 지원하기 위해 Excel이 항상 추가하는 부산물이다.
- `handlePaste`는 클립보드 아이템 중 `image/`로 시작하는 것을 최우선으로 찾아 즉시 업로드·삽입하고 `return true`로 종료한다.
- Excel 클립보드에는 항상 `image/png`가 포함되므로, 뒤에 있는 `text/html` 기반 표 처리 로직(및 markdown 재파서, 기본 ProseMirror 붙여넣기)에 도달하지 못하고 무조건 이미지 경로를 탄다.
- 이미지 우선 분기 자체는 스크린샷 붙여넣기(클립보드에 이미지만 있는 경우)를 지원하려는 의도였으나, "이미지가 있으면 이미지"로 판단해 이미지+표 HTML이 공존하는 Excel 케이스를 구분하지 못했다.
- Tiptap Table 확장(`@tiptap/extension-table` 등)은 이미 설치되어 있어, 이미지 분기만 우회하면 `text/html`의 `<table>`이 정상적으로 파싱된다는 것을 실제 브라우저 테스트로 확인했다.

## 수정

`components/document-editor.tsx`의 `handlePaste`에서 이미지 분기 진입 조건에 `<table>` 존재 여부 가드를 추가했다.

```ts
handlePaste(view, event) {
  // Excel/구글시트 등에서 셀을 복사하면 표 렌더링 이미지(image/png)가 text/html의
  // <table>과 함께 클립보드에 담긴다. 이때는 표 붙여넣기를 우선해야 하므로
  // <table>이 있는 경우에는 이미지 우선 처리를 건너뛴다.
  const pastedHtmlForImageCheck = event.clipboardData?.getData('text/html') ?? ''
  const hasPastedTable = /<table[\s>]/i.test(pastedHtmlForImageCheck)

  const imageFile = Array
    .from(event.clipboardData?.items ?? [])
    .find(item => item.type.startsWith('image/'))
    ?.getAsFile()

  if (imageFile && onUploadImageRef.current && !hasPastedTable) {
    // ... 기존 로직 그대로
  }
  // ...
}
```

판단 기준을 넓게(서식 있는 HTML 전반) 잡지 않고 `<table[\s>]`로 좁힌 이유:

- 스크린샷 붙여넣기 및 이미지 파일 복사는 `text/html`이 없거나 `<img>` 래퍼 정도만 있어 `hasPastedTable`이 `false`로 유지되어 기존 동작(이미지 삽입)이 보존된다.
- Word/구글독스 등에서 서식 있는 텍스트+인라인 이미지를 함께 복사하는 경우는 이번 수정 범위 밖으로 남겨, 회귀 위험을 최소화했다.

## 검증

Playwright로 dev 서버(`localhost:3000`)의 실제 에디터에 `ClipboardEvent('paste')`를 발생시켜 확인했다. Supabase 서비스 키로 임시 테스트 계정을 만들고 `localStorage`에 세션을 주입해 로그인을 우회했다.

사용자가 제공한 실제 대화 데이터(4열 × 8행)를 Excel 클립보드 형식(`text/html` `<table>` + `text/plain` TSV + `image/png`)으로 재현:

| 케이스 | 수정 전 | 수정 후 |
|---|---|---|
| `text/html`(`<table>`) + `text/plain` + `image/png` 동시 존재 (Excel 복사) | 이미지로 삽입 (`hasTable: false`) | **표로 삽입** (`hasTable: true`, `hasImage: false`) |
| `image/png`만 존재, `text/html` 없음 (스크린샷) | 이미지로 삽입 | 이미지로 삽입 (회귀 없음) |
| `text/html`(`<table>`) + `text/plain`만, 이미지 없음 | 표로 삽입 | 표로 삽입 (동일) |

이후 사용자가 실제 로컬 Excel에서 직접 복사·붙여넣기로 재확인했고, 표가 정상적으로 삽입됨을 확인했다.

정적 검증은 별도로 수행하지 않음(`tsc --noEmit` 미실행).

## 요약 (2) 페이지 저장 시 500 에러 (`column pages.files does not exist`)

위 붙여넣기 수정을 검증하는 과정에서, 페이지 내용을 저장할 때마다 `처리 실패 페이지를 저장하지 못했습니다.: column pages.files does not exist` 에러가 발생하는 것을 발견하고 함께 수정했다.

### 원인 분석

- `PATCH /api/pages`(`app/api/pages/route.ts`)가 업데이트 후 결과를 다시 읽어오는 `.select()` 절에 `files` 컬럼을 포함하고 있었다.
- `pages` 테이블에는 `files` 컬럼이 존재한 적이 없다(`supabase/migrations`의 마이그레이션 3개를 모두 확인했으나 추가된 적 없음). 코드베이스 전체에서도 이 select 절 한 곳에만 남아 있던 죽은 참조였다.
- `git log -S"files, created_by"`로 추적한 결과, 커밋 `32a2c49`("파일 업로드 관련 코드 롤백 및 레거시 정리", 2026-05-30)에서 원인이 발견됐다. 같은 커밋이 `/api/uploads` 라우트·`file-share-panel.tsx`·`notion-lite-app.tsx`의 파일 업로드 관련 코드는 정상적으로 제거했지만, `app/api/pages/route.ts`의 select 절만 `files` 컬럼을 **제거**하는 대신 **추가**하는 방향으로 diff가 반대로 적용됐다. 머지·리베이스 과정에서 방향이 뒤집힌 것으로 추정된다.
- 결과적으로 dev 브랜치에서 `PATCH /api/pages`(제목/내용/순서 저장)가 항상 500으로 실패했다.

혼선이 있었던 부분: 같은 에러가 `main` 브랜치로 전환해 `npm run dev`로 띄운 화면에서도 재현됐는데, `git show main:app/api/pages/route.ts`로 확인한 결과 main 코드에는 `files` 참조가 전혀 없었다. Turbopack이 브랜치 전환 전 dev 빌드의 캐시(`.next/`)를 재사용해 서버 쪽은 여전히 dev의 깨진 라우트를 서빙하고 있었던 것으로 판단, `.next` 캐시를 삭제한 뒤 재현 여부를 재확인해 원인을 dev 브랜치 코드로 좁혔다.

### 수정

`app/api/pages/route.ts`의 PATCH 핸들러에서 `.select()` 절의 `files` 컬럼을 제거했다.

```diff
- .select('id, workspace_id, parent_id, title, order_index, content, files, created_by, updated_by, created_at, updated_at')
+ .select('id, workspace_id, parent_id, title, order_index, content, created_by, updated_by, created_at, updated_at')
```

### 검증

- `.next` 캐시 삭제 후 `npm run dev`로 클린 빌드, 실제 페이지에서 편집 후 저장 시 500 에러 없이 정상 저장되는 것을 사용자가 직접 확인했다.

## 요약 (3) 사이드바 페이지 트리 depth 기반 기본 접힘 + 접힘 상태 영구 저장

기존에는 사이드바의 페이지 트리가 상위/하위 페이지 모두 펼쳐진 상태로 표시되어, 페이지가 많은 워크스페이스(예: 월/일자 계층 30여 개)에서 사이드바가 지나치게 길어졌다. Notion 등 프로덕션 관행에 맞춰 (a) 기본 접힘을 depth 기반으로 적용하고 (b) 사용자의 접힘/펼침 상태를 localStorage에 영구 저장하도록 개선했다.

### 배경 / 기존 동작

- `components/notion-lite-app.tsx`의 `collapsedPages`(`Set<string>`)가 빈 상태로 시작 → 기본값이 "전부 펼침".
- 접힘 상태가 어디에도 저장되지 않아 새로고침하면 다시 전부 펼쳐졌다.

### 수정

`components/notion-lite-app.tsx`에 다음을 추가/변경했다.

- 상수
  - `AUTO_COLLAPSE_FROM_DEPTH = 0` — 이 depth 이상(자식 있는 노드)은 첫 방문 시 접힘. `0`=최상위만 노출, `1`=최상위+1뎁스 노출. 저장된 상태가 있으면 이 기본값은 무시된다.
  - `COLLAPSED_STORAGE_PREFIX = 'cowork26:collapsed:'` — 워크스페이스별 접힘 상태 저장 키 프리픽스(`cowork26:collapsed:<workspaceId>`).
- 초기화 effect(워크스페이스별 1회, `autoCollapseInitRef: Set<string>`로 추적):
  1. localStorage에 저장된 접힘 상태가 있으면 복원. 이때 현재 존재하는 페이지 id로 필터링해 삭제된 페이지 id는 제외한다.
  2. 없으면(첫 방문) 각 페이지의 depth를 부모 체인으로 계산(순환 방어 `visited` 포함)해 `AUTO_COLLAPSE_FROM_DEPTH` 이상이고 자식이 있는 노드를 접힘 처리한다.
- 저장 effect: 초기화가 끝난 워크스페이스에 한해 `collapsedPages`가 바뀔 때마다 localStorage에 저장. 워크스페이스 전환 직후(초기화 전)에 이전 상태가 잘못 저장되지 않도록 init 완료 여부(`autoCollapseInitRef.has(...)`)로 가드한다.

동작 요약: 첫 방문 → depth 기본 접힘, 이후 사용자가 펼치거나 접은 상태는 같은 브라우저에서 새로고침·재접속 후에도 유지된다. 기기 간 동기화는 범위 밖(localStorage 특성).

### 검증

Playwright + 실제 dev 서버로 확인:

| 단계 | 결과 |
|---|---|
| 첫 방문 | 최상위만 노출(Welcome/2026.05/2026.06), 일자 하위 페이지 접힘 |
| chevron 클릭 | `rotate-90` 회전 + 자식 페이지 펼쳐짐 |
| 펼친 뒤 localStorage | 펼친 노드는 제외되고 아직 접힌 노드만 저장됨 확인 |
| **새로고침** | 펼쳐둔 상태 그대로 유지, 접힌 노드도 접힘 유지 |
| 워크스페이스 재방문(세션 내) | 수동 상태 유지(재접힘 없음) |

`npx tsc --noEmit` 통과.
