# DEV_260702 — Excel 셀 붙여넣기 시 이미지로 삽입되는 문제, 페이지 저장 500 에러, AGI 라우트 보안 검토

## 요약 (1) Excel 붙여넣기 → 이미지 삽입 문제

Excel에서 셀 범위를 복사해 에디터에 붙여넣으면 표가 아니라 셀 영역을 렌더링한 이미지(PNG)로 삽입되는 문제를 조사하고 수정했다. dev 브랜치에서 먼저 수정했고(커밋 `902f0cf`), 이후 main 브랜치를 최신화(`git pull`)하는 과정에서 동일한 버그가 main에도 유입된 것을 발견해 동일하게 수정했다.

원인은 `handlePaste`가 클립보드의 `image/*` 항목을 가장 먼저 검사·처리하는 구조였는데, Excel은 셀 복사 시 `text/html`(`<table>`)·`text/plain`(TSV)과 함께 셀 영역을 렌더링한 `image/png`를 항상 클립보드에 동봉하기 때문에, 표 데이터에 도달하기 전에 이미지 분기가 먼저 매칭되어 종료된 데 있었다.

### 원인 분석

확인된 증상:

- 외부(Excel)에서 셀들을 복사해 페이지에 붙여넣으면 표가 아니라 이미지로 들어간다.

붙여넣기 경로: `components/document-editor.tsx`의 `handlePaste(view, event)`.

```ts
handlePaste(view, event) {
  const imageFile = Array
    .from(event.clipboardData?.items ?? [])
    .find(item => item.type.startsWith('image/'))
    ?.getAsFile()

  if (imageFile && onUploadImageRef.current) {
    event.preventDefault()
    // ... PNG를 Storage에 업로드하고 <img> 노드 삽입
    return true          // ← 여기서 종료, text/html의 <table>은 검사되지 않음
  }
  // ...
}
```

근본 원인:

- 데스크톱 Excel은 셀 범위를 복사하면 클립보드에 `text/html`(`<table>` 마크업), `text/plain`(탭 구분 텍스트), `image/png`(셀 영역 렌더링 비트맵)를 **동시에** 담는다. `image/png`는 "그림으로 붙여넣기"를 지원하기 위해 Excel이 항상 추가하는 부산물이다.
- `handlePaste`는 클립보드 아이템 중 `image/`로 시작하는 것을 최우선으로 찾아 즉시 업로드·삽입하고 `return true`로 종료한다.
- Excel 클립보드에는 항상 `image/png`가 포함되므로, 뒤에 있는 `text/html` 기반 표 처리 로직(및 markdown 재파서, 기본 ProseMirror 붙여넣기)에 도달하지 못하고 무조건 이미지 경로를 탄다.
- 이미지 우선 분기 자체는 스크린샷 붙여넣기(클립보드에 이미지만 있는 경우)를 지원하려는 의도였으나, "이미지가 있으면 이미지"로 판단해 이미지+표 HTML이 공존하는 Excel 케이스를 구분하지 못했다.
- Tiptap Table 확장(`@tiptap/extension-table` 등)은 이미 설치되어 있어, 이미지 분기만 우회하면 `text/html`의 `<table>`이 정상적으로 파싱된다는 것을 실제 브라우저 테스트로 확인했다.

### 수정

`components/document-editor.tsx`의 `handlePaste`에서 이미지 분기 진입 조건에 `<table>` 존재 여부 가드를 추가했다.

```ts
handlePaste(view, event) {
  // Excel/구글시트 등에서 셀을 복사하면 표 렌더링 이미지(image/png)가 text/html의
  // <table>과 함께 클립보드에 담긴다. 이때는 표 붙여넣기를 우선해야 하므로
  // <table>이 있는 경우에는 이미지 우선 처리를 건너뛴다.
  const pastedHtmlForImageCheck = event.clipboardData?.getData('text/html') ?? ''
  const hasPastedTable = /<table[\s>]/i.test(pastedHtmlForImageCheck)

  const imageFile = Array
    .from(event.clipboardData?.items ?? [])
    .find(item => item.type.startsWith('image/'))
    ?.getAsFile()

  if (imageFile && onUploadImageRef.current && !hasPastedTable) {
    // ... 기존 로직 그대로
  }
  // ...
}
```

판단 기준을 넓게(서식 있는 HTML 전반) 잡지 않고 `<table[\s>]`로 좁힌 이유:

- 스크린샷 붙여넣기 및 이미지 파일 복사는 `text/html`이 없거나 `<img>` 래퍼 정도만 있어 `hasPastedTable`이 `false`로 유지되어 기존 동작(이미지 삽입)이 보존된다.
- Word/구글독스 등에서 서식 있는 텍스트+인라인 이미지를 함께 복사하는 경우는 이번 수정 범위 밖으로 남겨, 회귀 위험을 최소화했다.

dev 브랜치: 커밋 `902f0cf`("fix: Excel 셀 붙여넣기 시 이미지 대신 표로 삽입되도록 수정")로 반영.
main 브랜치: `git pull`로 origin/main을 50개 커밋 최신화하는 과정에서 AGI(짭비스) 관련 기능과 함께 이미지 붙여넣기 로직이 새로 유입되어 동일 버그가 재현됐고, 같은 패치를 main 작업 트리에도 적용했다(커밋 전).

### 검증

Playwright로 dev 서버(`localhost:3000`)의 실제 에디터에 `ClipboardEvent('paste')`를 발생시켜 확인했다. Supabase 서비스 키로 임시 테스트 계정을 만들고 `localStorage`에 세션을 주입해 로그인을 우회했다.

사용자가 제공한 실제 대화 데이터(4열 × 8행)를 Excel 클립보드 형식(`text/html` `<table>` + `text/plain` TSV + `image/png`)으로 재현:

| 케이스 | 수정 전 | 수정 후 |
|---|---|---|
| `text/html`(`<table>`) + `text/plain` + `image/png` 동시 존재 (Excel 복사) | 이미지로 삽입 (`hasTable: false`) | **표로 삽입** (`hasTable: true`, `hasImage: false`) |
| `image/png`만 존재, `text/html` 없음 (스크린샷) | 이미지로 삽입 | 이미지로 삽입 (회귀 없음) |
| `text/html`(`<table>`) + `text/plain`만, 이미지 없음 | 표로 삽입 | 표로 삽입 (동일) |

dev 브랜치는 사용자가 실제 로컬 Excel에서 직접 복사·붙여넣기로 재확인했고, 표가 정상적으로 삽입됨을 확인했다.
main 브랜치는 동일한 Playwright 재현 스크립트로 `hasImage: false / hasTable: true`를 확인했다(수정 직후, 사용자 수동 재확인은 별도 진행 예정).

정적 검증은 별도로 수행하지 않음(`tsc --noEmit` 미실행).

## 요약 (2) 페이지 저장 시 500 에러 (`column pages.files does not exist`) — dev 전용, 수정 완료

붙여넣기 수정을 검증하는 과정에서, dev 브랜치의 페이지 내용을 저장할 때마다 `처리 실패 페이지를 저장하지 못했습니다.: column pages.files does not exist` 에러가 발생하는 것을 발견하고 함께 수정했다.

### 원인 분석

- `PATCH /api/pages`(`app/api/pages/route.ts`)가 업데이트 후 결과를 다시 읽어오는 `.select()` 절에 `files` 컬럼을 포함하고 있었다.
- `pages` 테이블에는 `files` 컬럼이 존재한 적이 없다(`supabase/migrations`의 마이그레이션을 모두 확인했으나 추가된 적 없음). 코드베이스 전체에서도 이 select 절 한 곳에만 남아 있던 죽은 참조였다.
- `git log -S"files, created_by"`로 추적한 결과, 커밋 `32a2c49`("파일 업로드 관련 코드 롤백 및 레거시 정리", 2026-05-30)에서 원인이 발견됐다. 같은 커밋이 `/api/uploads` 라우트·`file-share-panel.tsx`·`notion-lite-app.tsx`의 파일 업로드 관련 코드는 정상적으로 제거했지만, `app/api/pages/route.ts`의 select 절만 `files` 컬럼을 **제거**하는 대신 **추가**하는 방향으로 diff가 반대로 적용됐다. 머지·리베이스 과정에서 방향이 뒤집힌 것으로 추정된다.
- 결과적으로 dev 브랜치에서 `PATCH /api/pages`(제목/내용/순서 저장)가 항상 500으로 실패했다.

혼선이 있었던 부분: 같은 에러가 `main` 브랜치로 전환해 `npm run dev`로 띄운 화면에서도 한 번 재현됐는데, 그 시점의 `git show main:app/api/pages/route.ts` 코드에는 `files` 참조가 전혀 없었다. Turbopack이 브랜치 전환 전 dev 빌드의 캐시(`.next/`)를 재사용해 서버 쪽은 여전히 dev의 깨진 라우트를 서빙하고 있었던 것으로 판단, `.next` 캐시를 삭제한 뒤 재현 여부를 재확인해 원인을 dev 브랜치 코드로 좁혔다. (main을 최신화하기 전 시점의 진단이며, 이후 main 자체는 이 버그를 가진 적이 없음을 재확인했다 — 아래 (3) 참고.)

### 수정

`app/api/pages/route.ts`의 PATCH 핸들러에서 `.select()` 절의 `files` 컬럼을 제거했다.

```diff
- .select('id, workspace_id, parent_id, title, order_index, content, files, created_by, updated_by, created_at, updated_at')
+ .select('id, workspace_id, parent_id, title, order_index, content, created_by, updated_by, created_at, updated_at')
```

dev 브랜치: 커밋 `f6795e7`("fix: PATCH 메서드에서 select 쿼리 수정")로 반영.

### 검증

- `.next` 캐시 삭제 후 `npm run dev`로 클린 빌드, 실제 페이지에서 편집 후 저장 시 500 에러 없이 정상 저장되는 것을 사용자가 직접 확인했다.

## 요약 (3) main 브랜치 검토 — 최신화 전/후 상태 차이

### 최신화 전 (로컬 main이 origin/main보다 50커밋 뒤처진 상태)

- main의 `handlePaste`에는 이미지 처리 로직 자체가 없었고(순수 markdown 표/코드블록 파서만 존재), `pages.files` 참조도 없었다. 즉 이 시점의 main에는 위 두 버그가 모두 존재하지 않았다.
- Playwright로 직접 재현 테스트한 결과 Excel 클립보드(표+PNG) 붙여넣기가 정상적으로 표로 삽입됐고, `PATCH /api/pages`도 200을 반환했다.

### `git pull`로 origin/main 최신화 이후

- 로컬 main이 `origin/main`보다 50개 커밋 뒤처져 있었고(`git status`가 지속적으로 경고), UI가 눈에 띄게 구식으로 보이는 것을 계기로 최신화를 진행했다.
- `.gitignore`에 대한 사소한 로컬 변경(사용자가 무시해도 된다고 확인)만 `git restore`로 되돌린 뒤 `git pull`로 fast-forward, 48개 파일·7265줄 삽입 규모의 변경을 받았다. 이 중 `app/api/agi/route.ts`, `components/floating-ai-button.tsx` 등 AGI(짭비스) 연동 기능과 함께, dev에서 고쳤던 것과 동일한 이미지 우선 `handlePaste` 로직이 main에도 함께 유입됐다.
- 재검증 결과 main도 dev와 동일하게 Excel 붙여넣기 시 이미지로 삽입되는 버그를 갖게 됐음을 확인, 위 (1)과 동일한 `<table>` 가드 수정을 main 작업 트리에도 적용했다(수정 시점 기준 아직 커밋 전).
- `pages.files` 참조 버그는 최신화 이후에도 main에 유입되지 않았다(grep으로 재확인, 미검출).

## 요약 (4) `app/api/agi/route.ts` 보안 검토 (자동 리뷰)

main 최신화로 새로 유입된 `app/api/agi/route.ts`에 대해 자동 보안 리뷰가 실행되어 다음 문제가 보고됐다. 이 파일은 이번 세션에서 작성하지 않았으며, 리뷰 결과만 기록한다.

| 심각도 | 문제 | 위치 |
|---|---|---|
| CRITICAL | 인증 없는 원격 코드 실행 — `POST /api/agi`가 인증 검사 없이 호출 가능하며, 호출 시 서버에서 `spawn(exePath, ['--background'], ...)`으로 실행 파일을 구동함 | `app/api/agi/route.ts` |
| CRITICAL | 평문(HTTP) 다운로드 후 무검증 실행 — `JJAPVIS_SERVER_URL` 기본값이 `http://49.142.52.133:1777`(HTTPS 아님)이며, 여기서 받은 `AGI-client.exe`를 서명·해시 검증 없이 디스크에 쓰고 실행함(MITM으로 임의 코드 실행 가능) | `app/api/agi/route.ts` |
| MEDIUM | 신뢰할 수 없는 PID 파일 기반 프로세스 종료 — `DELETE`가 PID 파일을 읽어 `kill(pid)` 호출, 해당 PID가 실제로 자신이 띄운 프로세스인지 검증하지 않고 `DELETE`도 인증 없음 | `app/api/agi/route.ts` |

### 현재 위험도 평가

- 코드 경로는 `const ENABLE_AGI = process.env.NEXT_PUBLIC_ENABLE_AGI === 'true'`로 게이트되어 있고, `POST`/`GET`/`DELETE` 모두 진입 즉시 `if (!ENABLE_AGI) return disabledResponse()`로 반환된다.
- `.env.example`에 `NEXT_PUBLIC_ENABLE_AGI=false`가 기본값으로 문서화되어 있고, 로컬 `.env`/`.env.local`에는 이 변수 자체가 설정돼 있지 않아(→ `undefined !== 'true'` → `false`) 로컬에서도 비활성 상태다.
- `npx vercel env ls production`으로 실제 Vercel Production/Preview 환경변수를 확인한 결과 `NEXT_PUBLIC_ENABLE_AGI`가 등록되어 있지 않다. 즉 **현재 배포본(main)에서도 AGI 기능은 비활성 상태**이며, 위 취약점 코드 경로에 도달하지 않는다.
- 다만 `JJAPVIS_SERVER_URL` / `NEXT_PUBLIC_JJAPVIS_SERVER_URL`은 Production/Preview에 이미 등록되어 있어(41일 전 생성), 플래그만 켜면 즉시 취약점이 활성화될 수 있는 상태다.

### 후속 조치 (미착수)

플래그를 켜기 전에 최소한 다음이 선행되어야 한다:

1. `POST`/`DELETE` 핸들러에 `getUserFromRequest` 기반 인증(및 워크스페이스 owner 등 역할 검사) 추가.
2. `SERVER_URL`을 HTTPS로 강제하고, 다운로드한 실행 파일을 SHA-256 등으로 사전에 고정한 값과 대조해 불일치 시 실행 거부.
3. PID 파일 권한을 0600으로 좁히고, kill 대상 PID가 실제로 이 프로세스가 띄운 자식 프로세스인지 in-memory 참조나 시작 시각 대조 등으로 검증.
